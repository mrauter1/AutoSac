05 · Reasoning

Decisions, strengths, constraints

The highest-leverage architectural facts for evaluating changes and operational risk.

Why PostgreSQL is also the queue
It keeps ticket state, AI work, and integration outbox records in one transactional boundary. Partial unique indexes, row locks, SKIP LOCKED, heartbeats, and claim tokens replace a separate broker.
  • Strength: inspectable and operationally simple.
  • Tradeoff: polling latency and PostgreSQL-specific coupling.
Model output is not publication authority
Pydantic validates structure; the registry validates eligibility; publication policy separately checks route allowance, confidence, risk, and reply presence. Unsafe recommendations are downgraded to draft or manual review.
Two coordinated durable stores
PostgreSQL owns business state; disk owns bytes and AI evidence. Routes clean up files when SQL fails, but there is no cross-resource transaction. Shared, persistent storage is therefore a deployment requirement.
Defense in depth
Opaque hashed sessions, two-stage CSRF, role/ownership checks, safe redirects, sanitized Markdown, generated attachment paths, schema-constrained output, read-only Codex, and encrypted Slack tokens protect different trust boundaries.
Stale-work protection
One active AI run per ticket, deferred requeue, input fingerprints, worker ownership, heartbeats, recovery lineage, outbox dedupe keys, delivery claims, and dead letters prevent stale or duplicate effects.
Change-risk hotspots
The largest coordination modules are app/routes_ops.py, shared/ticketing.py, worker/step_runner.py, worker/slack_delivery.py, and superloop/superloop.py. Changes there cross multiple state or infrastructure boundaries.
Separate product boundary: superloop/ is a co-located development-orchestration CLI. It has no imports, database tables, or runtime calls connecting it to the AutoSac web/worker application.
